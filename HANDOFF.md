# MP-CRM — техническая документация для переноса на нового клиента

Этот файл — для нового чата Claude (или любого разработчика), который будет
делать копию системы под другого клиента. Он не про ЭТУ конкретную компанию
(её товары/поставщиков трогать не нужно), а про то, как устроена система,
какие решения приняты и почему, и на что обратить внимание при копировании.

Кодовая база уже полностью рабочая и задеплоенная — это не прототип, а
эксплуатируемая система с реальными интеграциями. Схема БД (`prisma/schema.prisma`)
уже сама по себе подробно прокомментирована по-русски — читать её вместе с этим
файлом, я не дублирую то, что уже объяснено там.

## 1. Что это за система

CRM для продавца на маркетплейсах (Wildberries, Ozon, Яндекс.Маркет) + опционально
B2B-продажи. Закрывает полный цикл: товары → поставщики (Китай и/или Россия) →
поставки → остатки на своих и площадочных складах → листинги на площадках →
продажи → юнит-экономика → планирование новых закупок. Мультитенантная —
несколько независимых компаний в одной БД, у каждой свои данные, свои API-ключи
площадок, свои пользователи.

Ключевая идея, вокруг которой всё построено: **у каждого товара есть единая
внутренняя карточка (`Product`)**, которая матчится с "тем же" товаром на всех
площадках через `MpListing`, и вся аналитика/юнит-экономика/планирование строится
поверх этой карточки, а не поверх листингов площадок по отдельности.

## 2. Стек

- **Next.js 14 App Router + TypeScript**, серверные компоненты по умолчанию.
- **Prisma ORM + PostgreSQL** (в проде — Supabase, через connection pooler).
- **Auth.js v5** (NextAuth), credentials-провайдер, пароли — bcryptjs.
- **Vercel** (Hobby-план в текущем проекте — это накладывает жёсткое ограничение,
  см. раздел 5).
- **Supabase** — Postgres + Storage (фото товаров).
- **Resend** — email (восстановление пароля).
- **ExcelJS** — импорт/экспорт всех Excel-файлов (загрузка прайсов площадок,
  выгрузки для закупщика/склада).
- Без Redis/очередей/воркеров — все синки идут прямо в serverless-функциях
  Vercel по cron или по кнопке.

## 3. Мультитенантность — ключевой архитектурный паттерн

Это единственная по-настоящему нетривиальная архитектурная находка проекта,
её стоит скопировать один в один, а не изобретать заново.

- Каждая модель в схеме (кроме `Company`/`User`/`PasswordResetToken`, см.
  комментарий в `lib/prisma.ts`) имеет колонку `companyId`.
- `lib/tenantContext.ts` — `AsyncLocalStorage`-контекст: `runWithTenant(session, fn)`
  оборачивает тело page.tsx/route.ts сразу после получения сессии, дальше по
  цепочке `await` companyId нигде руками не передаётся.
- `lib/prisma.ts` — Prisma Client Extension, который на КАЖДЫЙ вызов
  `prisma.<model>.<operation>()` сам домешивает `companyId` из текущего контекста
  в `where`/`data`. Это значит: ни один из ~80 файлов, читающих Prisma, не пишет
  `where: { companyId }` руками — фильтрация включена глобально одним местом.
  Это же значит: если писать сырой Prisma-скрипт для диагностики/миграции данных
  (не через приложение) — этот extension не работает, там `companyId` нужно
  фильтровать вручную.
- `$queryRaw`/`$executeRaw` эту обёртку не проходят — в тех немногих местах, где
  они используются (массовые батч-вставки), `companyId` добавлен явно.
- Практическое следствие: **копируя проект под нового клиента, эта часть не
  меняется вообще** — просто у нового клиента будет своя строка `Company`, всё
  остальное само изолируется.

## 4. Данные площадок и куда они попадают — обзор моделей

Схема разбита на пронумерованные секции с комментариями прямо в файле:
1. Компании/пользователи, 2. Товары, 3. Поставщики, 4. Поставки из Китая,
5. Маркетплейсы и листинги, 6. Склады и остатки, 7. Заказы, 8. Юнит-экономика,
9. Аналитика остатков/продаж, 10. Задачи (канбан).

Самое важное, что нужно понимать НЕ из комментариев в схеме, а из практики
эксплуатации:

- **`Product` — центральная сущность.** `sku` — наш внутренний код, `vendorCode` —
  артикул, под которым товар известен ПОСТАВЩИКУ (для российских поставщиков это
  реально используется при оформлении заказа, см. раздел 8) и одновременно самый
  надёжный ключ для матчинга с площадками (часто совпадает на нескольких
  площадках сразу, в отличие от числового SKU конкретной площадки).
- **`MpListing`** — связь Product↔Marketplace, по одной на каждую пару
  товар+площадка. `fulfillmentSchema` (FBO/FBS, строка, не enum) и
  `lifecycleStatus` (SELLING/NEW_TESTING/PHASING_OUT) — оба поля заполняются
  ВРУЧНУЮ из файлов поставщика, площадка их не отдаёт через API.
- **`MpImportItem`** — очередь на сопоставление. Любой синк с площадки, который
  не смог однозначно найти `Product` (по существующему `MpListing`, штрихкоду
  или `vendorCode`), кладёт строку сюда со статусом `PENDING` — **`Product`
  никогда не создаётся автоматически без подтверждения** (кроме специального
  bulk-create-placeholders потока для явно новых товаров, см. раздел 7). Ручное
  сопоставление — страница `/matching`.
- **Несколько магазинов одной площадки** (например, два разных кабинета Ozon)
  поддерживаются: `Marketplace.code` НЕ уникален, уникально `(companyId, name)`
  — компания сама называет магазины "Ozon"/"Ozon 2". Везде в коде, где нужно
  различить магазины, используется `marketplaceId`, а не `code`.
- **Аналитика остатков — три уровня детализации**, все пишутся из
  `lib/stockImportSync.ts`:
  - `ProductStockAnalytics` — общий остаток + скорость продаж по товару на
    площадке (за 28 дней; параллельно с недавних пор считается ещё окно за 7
    дней — `avgDailySalesQty7d` — чтобы видеть недавний всплеск/просадку спроса
    раньше, чем это отразится на месячном среднем).
  - `ProductClusterAnalytics` / `ProductWarehouseAnalytics` — то же самое в
    разрезе региона/физического склада (нужно для распределения новой поставки
    по городам). **Известная проблема**: для Ozon кластерная разбивка строится
    из ОТДЕЛЬНОГО API-вызова (`fetchOzonStockByWarehouse` + `fetchOzonClusters`)
    и может систематически недосчитывать часть остатка, если склад не
    смаппился на известный кластер — строка тогда молча пропускается (см.
    `lib/stockImportSync.ts`, цикл `for (const row of warehouseRows) { if
    (!clusterName) continue; ... }`). Это НЕ баг синхронизации, а разрыв между
    двумя API-эндпоинтами Ozon — стоит иметь в виду при копировании: сумма по
    городам может быть меньше общего остатка, и это ожидаемо, а не ошибка.
  - `ProductCardHealth` — только Ozon (контент-рейтинг + индекс цены).
- **Юнит-экономика (`UnitEconomics`)** — одна строка на
  `(productId, marketplaceId, periodMonth)`. Важно: есть legacy-поле
  `marketplace: MarketplaceCode?` (enum) — оно НЕ является ключом идентичности
  (это было бы неверно при нескольких магазинах одного кода), настоящая связь —
  через `marketplaceId`. Поле оставлено для быстрых фильтров/подписей.

## 5. Жёсткое ограничение Vercel Hobby (300 секунд) и как вокруг него построена архитектура синков

Это второй по важности архитектурный урок проекта — если у нового клиента тоже
будет Hobby-план (или просто похожий serverless-таймаут), это повторится один в
один.

- **Каждый serverless-вызов ограничен 300 секундами.** Полный синк одной площадки
  (юнит-экономика + воронка + сезонность + импорт остатков + [для Ozon —
  здоровье карточки]) в одном вызове НЕ укладывается.
- Решение: каждый под-синк — **отдельный route + отдельная cron-запись** в
  `vercel.json`, все на одно и то же время (`"0 21 * * *"` = 00:00 МСК), но как
  независимые serverless-функции, каждая со своим бюджетом в 300с. Сейчас 10
  cron-записей: 1×WB (WB укладывается целиком в одну функцию), 5×Ozon
  (unit-economics/funnel/seasonality/stock-import/card-health), 4×Yandex
  (unit-economics/funnel/seasonality/stock-import).
- `lib/dailySync.ts` — общая точка входа для каждого под-синка,
  `runMarketplaceSubSync(code, subSyncKey, fn)` находит ВСЕ строки `Marketplace`
  этого кода у компании (может быть несколько магазинов) и гоняет их
  **параллельно** (`Promise.all`) — специально: последовательно второй магазин
  той же площадки удваивал общее время и упирался в лимит (реальный инцидент,
  не гипотеза, см. комментарий в файле).
- **Даже при этом бывает, что синк не укладывается** — известная текущая
  проблема: у второго магазина Ozon ("Ozon 2") `stock-import` регулярно не
  успевает (реальные транзакции за месяц, полная пагинация — это может занять
  больше 300с само по себе, безотносительно к параллельности). При копировании
  под нового клиента с одним магазином на площадку это не проявится; если у
  клиента будет несколько магазинов одной площадки — стоит сразу закладывать
  дальнейшее дробление синка (например, по типу операции внутри stock-import) или
  переход на план с бо́льшим лимитом.
- `app/api/cron/*/route.ts` защищены заголовком `Authorization: Bearer
  <CRON_SECRET>` (Vercel сам его подставляет по расписанию) — НЕ через логин
  пользователя. `middleware.ts` пропускает эти пути без сессии, сам роут
  сверяет секрет.
- `app/api/daily-sync/*/route.ts` — те же функции, но для ручного вызова из UI
  (кнопка "Обновить всё", `app/RefreshAllButton.tsx`) с реальной сессией
  пользователя вместо cron-секрета.
- **Supabase pooler имеет лимит одновременных соединений** (`EMAXCONNSESSION` —
  "max clients reached in session mode", pool_size обычно 15) — если запускать
  несколько синков/диагностических скриптов ПАРАЛЛЕЛЬНО (включая ручные
  `tsx`-скрипты с прямым `PrismaClient`, не через приложение), это легко
  словить. Решение — запускать последовательно, не через `Promise.all`/несколько
  фоновых curl одновременно.

## 6. Клиенты API площадок (`lib/wbApi.ts`, `lib/ozonApi.ts`, `lib/yandexMarketApi.ts`)

Credentials хранятся НЕ в `.env`, а в `Marketplace.credentials` (JSON) — вводятся
пользователем на странице `/settings/integrations` для каждого магазина отдельно.
Форма credentials разная под каждую площадку (токен WB / clientId+apiKey Ozon /
токен+businessId+два campaignId у Яндекса) — см. типы в соответствующих
`*Api.ts` файлах.

Накопленные за время эксплуатации особенности API площадок — это ценность,
которую тяжело найти заново, стоит перечитать перед повторной интеграцией:

**Wildberries**
- `/api/v1/supplier/orders` с `dateFrom` старше ~35 дней ОБРЕЗАЕТ ответ
  посередине (не ошибка, просто битый JSON) — окно синка ограничено константой
  в коде, а не пагинируется.
- Реальный rate-limit — 429 регулярно возникает даже при обычной частоте
  запросов, синк должен просто ретраиться на следующий cron-прогон, а не пытаться
  агрессивно ретраить сразу.
- Запросы к WB API должны идти ПОСЛЕДОВАЛЬНО, не параллельно (несколько тяжёлых
  запросов сразу давали обрыв соединения).

**Ozon**
- `/v3/finance/transaction/list`: один физический возврат/отмена/невыкуп
  разбивается Ozon на 2-4 отдельные транзакции с типом `"returns"` (доставка,
  обработка, получение — разные строки услуг для ОДНОЙ и той же единицы товара).
  Без дедупликации по `posting_number` количество возвратов считается в 2-4 раза
  больше реального — см. `lib/unitEconomicsSync.ts`.
- Диапазон дат ограничен ~месяцем ("too long period, only one month allowed").
- `/v3/posting/{fbo,fbs}/list` — единственный источник настоящего % выкупа для
  Ozon: `financial_data.products[]` (надёжная цена) и top-level `products[].sku`
  (единственное место с sku прямо на позиции) — это ДВА разных под-объекта одной
  и той же строки, нужны оба поля из разных мест.
- Кластерная разбивка остатков строится из ОТДЕЛЬНОГО эндпоинта
  (`fetchOzonStockByWarehouse` + `fetchOzonClusters`) и может терять часть
  остатка на несмаппленных складах — см. раздел 4.

**Яндекс.Маркет — самая хрупкая интеграция, будьте осторожны**
- `/reports/shows-sales/generate` ограничен 1 запросом в 10 минут на businessId
  — для регулярного синка непригоден, вместо него используются прямые запросы
  `/campaigns/{id}/orders` (без такого лимита, но с максимум 30 днями диапазона
  за раз).
- Обнаружена (и НЕ разрешена до конца) проблема: даже после устранения таймаутов
  (разбиением на отдельные cron) `syncYandexStockImport` иногда получает
  `{"status":"ERROR","errors":[{"code":"INTERNAL_ERROR"}]}` от самого Яндекса,
  причём воспроизводится только через реальный cron-вызов, не через
  последовательное ручное тестирование тех же самых нижележащих запросов по
  отдельности. Причина не найдена несмотря на несколько системных попыток
  (сериализация запросов, устранение дублирующихся вызовов). **При копировании
  под нового клиента стоит закладывать время на то, что интеграция с Яндекс.
  Маркетом потребует повторной отладки** — это не разовая случайность, а
  повторяющееся поведение их API/инфраструктуры.
- Дневная гранулярность заказов у Яндекса недоступна для отчёта "Реализация
  товаров" (`granularity=MONTH` в `MarketplaceDailyFunnel`, в отличие от
  `DAY` у WB/Ozon).

## 7. Матчинг товаров с площадками (`lib/matching.ts`)

Единая функция `upsertImportItem({marketplaceId, mpSku, barcode, name,
vendorCode?})`, вызывается из КАЖДОГО синка остатков (WB/Ozon/Яндекс) и из
ручных Excel-импортов. Приоритет сопоставления:
1. Уже есть `MpListing` на этот `(marketplaceId, mpSku)` — просто освежаем.
2. Штрихкод товара совпал с известным `Product.barcode`.
3. `vendorCode` совпал (используется вторым магазином одной площадки — общий
   артикул продавца может совпадать между двумя кабинетами Ozon, хотя числовой
   SKU площадки — нет).
4. Ничего не нашли — кладём в `MpImportItem` со статусом `PENDING`, ждём ручного
   выбора на `/matching`.

`ensureListingForMatch()` — важный нюанс: при матче по штрихкоду/vendorCode
(не через уже существующий `MpListing`) обязательно нужно СОЗДАТЬ реальную
строку `MpListing`, иначе товар матчится для остатков, но не появляется как
"активный листинг" нигде в аналитике/планировщике — это был реальный
production-баг (21 "невидимый" товар), исправленный именно так.

## 8. Планировщик поставок (`/batches/plan`, `/batches/plan-ru`)

Две отдельные страницы с ОБЩИМ UI-компонентом (`app/batches/plan/PlannerForm.tsx`)
и общей логикой расчёта (`app/batches/plan/plannerData.ts`), различаются только
фильтром `Supplier.country` (`CHINA`/`RUSSIA`, enum `SupplierCountry`) — Китай и
Россия принципиально разные по горизонту планирования (лид-тайм ~120 дней через
таможню vs дни-недели), поэтому разведены по разным страницам, но способ
оформления заказа (та же модель `Batch`/`BatchItem`, тот же статус логистики)
общий для обоих.

Что считает `plannerData.ts` на товар: остаток + скорость продаж (по всем
площадкам, где товар активен) → сколько дней до конца остатка → с учётом
сезонного коэффициента (посчитанного по истории продаж, `lib/seasonality.ts`,
либо ручного из карточки товара, если истории нет) и лид-тайма поставщика →
рекомендованное количество заказа, поднятое до MOQ поставщика, если необходимо.

Планировщик поддерживает вкладки: "Общая", по каждому поставщику (для
раздельного оформления заказа разным поставщикам), по каждой площадке. При
раскрытии товара — дерево площадка → город/кластер (не всегда полное, см.
известную проблему в разделе 4).

Три вида выгрузки из планировщика:
1. **Excel для закупщика** (`/api/batches/plan/export`) — сгруппировано по
   поставщику, с разбивкой количества по площадкам.
2. **Раскладка по городам для склада** (`/api/batches/plan/warehouse-export`,
   логика — `lib/warehouseDistribution.ts`) — товар → площадка → город/кластер →
   количество, ДО оформления реальной поставки (по выбранным строкам с
   проставленным количеством). Та же логика используется ПОСЛЕ оформления —
   `/api/batches/[id]/warehouse-export`, для уже реальной `Batch`.
3. Сама поставка (`POST /api/batches/plan`) создаёт `Batch` + `BatchItem[]`.

## 9. Что специфично для ЭТОЙ компании (не переносить бездумно)

- Домен — автозапчасти/автотовары (бренд AVS), поставщики "Грал"/"Маяк"/
  "Сонатекс" — это данные конкретного клиента, не часть платформы.
- Ручные Excel-импорты заточены под конкретные форматы отчётов, которые скачивает
  ИМЕННО ЭТОТ продавец из личных кабинетов площадок (`lib/wbImport.ts`,
  `lib/ozonImport.ts`, `lib/yandexImport.ts`, плюс парсинг многолистовых
  внутренних файлов учёта поставщика вида "Заказы, сток ...xlsx" — колоночная
  структура таких файлов у разных клиентов почти наверняка будет другой,
  парсер придётся переписывать под конкретный файл).
- `SupplierCountry`/два планировщика имеет смысл только если у нового клиента
  тоже смешанные китайские+российские поставщики с разным лид-таймом; если нет —
  можно упростить до одного планировщика.

Всё остальное (мультитенантность, паттерн синков, модель товар↔листинг↔остаток,
юнит-экономика, канбан-доска задач) — универсальная платформенная часть,
переносится как есть.

## 10. Разворот под нового клиента — практические шаги

1. Скопировать репозиторий целиком (папку проекта) в новое место.
2. Создать НОВЫЙ проект Supabase (не переиспользовать текущий — там чужие
   данные) → взять `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
3. `npx prisma db push` на пустую БД (или `migrate deploy`, если сохранять
   историю миграций) — таблицы создадутся с нуля, реальных данных переносить не
   нужно.
   - **Известная особенность окружения**: локальный `prisma migrate dev`
     стабильно падает с `P1001` через Supabase pooler (не баг проекта — сетевая
     специфика пулера) — рабочий обход: `prisma db push` (иногда с 2-8
     повторами из-за флакающего соединения), затем вручную написать
     `migration.sql` и `prisma migrate resolve --applied <name>`, чтобы
     зафиксировать в `_prisma_migrations` без повторного выполнения.
4. Создать новый проект на Vercel, подключить репозиторий, прописать все
   переменные окружения из `.env.example` (включая новый `AUTH_SECRET`,
   `CRON_SECRET` — сгенерировать заново, не копировать чужие).
5. Задеплоить, зарегистрировать первого пользователя через `/signup` (это
   автоматически создаёт новую `Company`), одобрить его (см. `User.approved` —
   либо руками в БД для самого первого, либо через `/admin`, если email в
   `SUPERADMIN_EMAILS`).
6. Завести площадки на `/marketplaces`, ввести реальные API-ключи клиента на
   `/settings/integrations`.
7. Проверить каждый cron/ручной синк по отдельности перед тем как полагаться на
   автоматику по расписанию — особенно Яндекс.Маркет (см. раздел 6).
